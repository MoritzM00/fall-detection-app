# Prepared video input

The user can edit start/end time, frame count (2–32), sampling FPS (up to 30), and square center-crop size. The default is the thesis preset: 16 frames at 7.5 FPS, 448 × 448. A changed setting is an experimental configuration, not a validated thesis baseline. End time, frame count, and FPS stay linked by `end = start + (frame_count - 1) / fps`.

`POST /prepared-inputs` decodes the stored source with PyAV, choosing the nearest real PTS frame for each requested time. It resizes by the shortest edge, center crops, and writes a `uint8` RGB array, lossless PNGs for inspection, JPEGs for online vLLM, and a manifest with actual times, source PTS, frame hashes, and a bundle hash. The ID is derived from video asset ID, source content, selected settings, and preprocessing version. Including the asset ID keeps identical uploads associated with their own manifests. Existing prepared IDs remain readable. The UI waits for that manifest and displays the saved JPEGs before enabling analysis. `POST /analysis-jobs` accepts the matching prepared input ID and snapshots its settings.

Preparation version `pyav-pillow-online-jpeg-v4` maps source PTS to the browser playback timeline by subtracting the video stream start time (including negative origins). When stream start metadata is absent, the first timestamped decoded frame defines zero. The original `source_pts` remains in the manifest; `actual_seconds` and requested windows use the relative timeline. Requests before the first available frame are rejected rather than silently filled. Native browser playback controls can expose absolute stream times after seeking; selection and frame captions remain relative to the stream origin. Chromium coverage compares a prepared frame at 0.4 seconds with playback at source time 5.4 seconds for a clip starting at 5 seconds.

Preprocessing v4 also invalidates earlier bundles. The final frame is valid through its presentation timestamp plus its positive decoded duration. If that duration is unavailable, preparation uses the last positive inter-frame interval, then the stream average frame rate, then stream duration; without any of these it accepts only through the last timestamp. An exact-end request selects the final frame, matching the UI's duration fit. A one-microsecond tolerance handles floating-point rounding; requests beyond that extent fail. This policy applies to app preparation and does not change the research baseline.

The worker verifies the RGB bundle and the saved JPEG hashes. For both the local mock and a configured vLLM server, it sends those JPEG files as `data:video/jpeg;base64,...` in one `video_url` content part, with `media_io_kwargs.video` containing FPS, frame indices, duration, and `do_sample_frames: false`. This follows vLLM's [pre-extracted frame sequence format](https://docs.vllm.ai/en/latest/features/multimodal_inputs/#pre-extracted-frame-sequences-with-media_io_kwargs). The UI and request use the same encoded JPEG bytes. Browser and server JPEG decoding may have small implementation differences, so this establishes encoded-frame identity rather than strict decoded-pixel identity.

The worker uses the online chat-completions API. It does not call `LLM.generate` or use the research repository's offline tensor path. The installed vLLM version and Qwen3-VL processor still need an integration test on the GPU server to verify request-level `media_io_kwargs`, temporal metadata, and the model's handling of the JPEG frame sequence.

The synthetic corridor sample has no decodable media, so it keeps its simulated preview and mock-only result. Its output must not be treated as evidence about frame preparation or model behavior.
